Until September 2026, this Turflang function compiled:

```turf
fn make(): &N {
    mut n: N = N::default();
    n.val = 42;
    return &n;
}
```

`n` lives in `make()`'s stack frame, and that frame is gone once `make()` returns. The caller ends up with a
reference to memory that the next function call will reuse, so it might read `42`, or `0`, or whatever that call
left behind. The compiler now rejects it:

```text
── error at line 4, col 5 [E086 · dangling reference escape]

  I cannot let a reference into this function's own local storage be returned, because it would dangle
  when this function returns.

  Hint: Copy it onto the GC heap first with `heap(value)`, which gives a reference that outlives this
  function, or return or store a reference you received as a parameter instead of a local's.
```

The check is a compiler pass called `EscapePass`. This article covers what it tracks, why Turflang does it
without lifetime annotations, and sixteen cases a fuzzer found that the pass got wrong.

## The rule

Turflang has two safe reference types: `&T`, which is never null, and `&?T`, which you have to check before
using. Neither type says where the target lives. A reference can point into the GC heap, into the caller's
memory, or into the current function's own frame. Only the last one can dangle, and only if the reference
outlives the call.

The [language specification](https://github.com/turf-lang/turf-lang/blob/master/docs/development/FREEZE.md)
lists the places a reference into the current frame must never reach. We call these sinks. Each one is a way for
a value to outlive the function that made it:

<Figure caption="The six sinks. A reference into the current frame that reaches any of them is E086. The usual fix is heap(), which copies the value to the GC heap and returns a reference that lives as long as anyone holds it.">
  <EscapeSinks />
</Figure>

To enforce this, the pass tracks where every reference came from at every point in the function. We call that
its provenance:

| Provenance | Means | At a sink |
| --- | --- | --- |
| `Stack` | points into this frame: `&n`, `&n.f`, `&a[i]` of a local array | E086 |
| `MayStack` | `Stack` on at least one path that reaches here | E086 |
| `Param` | came in from the caller, `self` included | allowed |
| `Heap` | from `heap()`, or read through something that is | allowed |
| `Unknown` | the pass cannot tell | allowed |

When the pass can't classify a value, it lets it through. We made that choice in the first version, and most of
the rest of this article follows from it.

## Why there is no borrow checker

Rust handles this with lifetimes. Every reference carries a region in its type, and the compiler checks at every
use that the region is still alive. It works, but it adds syntax and takes time to learn. We wanted Turflang to
have neither, so there are no lifetime annotations, no borrow checker, and almost no reasoning across function
boundaries (one small exception comes up below).

The trade-off is that the pass can't catch everything. It looks at one function at a time, understands a fixed
set of expression shapes, and treats anything else as `Unknown`. In return it promises never to report an error
on a correct program: every E086 is a real escape. Some real escapes, in shapes the pass doesn't model, still get
through, and the [design
record](https://github.com/turf-lang/turf-lang/blob/master/docs/development/changes/FDN-002.md) lists them.

That promise was tested on day one. Running the new pass over the compiler's own test suite flagged two correct
programs. One cast `&pt1` to `Point*` and pushed it into a `List<Point*>` that never left the function. The other
took `&l.data[1]` on a `List`'s heap-allocated buffer. We fixed both by having the pass track less. A cast to a
raw pointer now drops out of tracking entirely, since that's unsafe code, and `&expr[i]` counts as `Stack` only
when the type says `expr` is a local fixed-size array.

## How the pass works

`EscapePass` ([documented
here](https://github.com/turf-lang/turf-lang/blob/master/docs/architecture/pointers_and_references.md)) is a
forward dataflow analysis over the function's control-flow graph, and it runs alongside the pass that checks for
null dereferences. At each point it keeps a map from a *place* to a provenance. A place is a variable, or a path
inside a value variable such as `h.head` or `a[0].next`. A place that isn't in the map gets a default: `Param`
for a reference parameter, `Unknown` for anything else.

Each statement updates the map. `p = &n` sets `p` to `Stack`, `p = heap(n)` sets it to `Heap`, and `h.head = p`
copies `p`'s provenance to `h.head` and forgets whatever was known under the old value. When a statement hands a
value to a sink, the pass checks that value's provenance, and for a struct or array it checks every place stored
inside it too.

Where control flow joins, such as after an `if` or at the top of a loop, the maps from each incoming path are
merged place by place:

<Figure caption="Merging two paths' provenance for one place. If they agree, the result is the same. Stack on either side gives MayStack, which is flagged at a sink just like Stack. Any other disagreement gives Unknown, which is never flagged.">
  <MergeGrid />
</Figure>

The pass repeats this until the maps stop changing, and only then reports errors.

Two details matter as the language grows. The statement visitor walks into any kind of node it doesn't handle
explicitly, so a new kind of expression is still searched for escapes nested inside it. The list of collection
methods that store values (`push`, `set`, `put`, `add`, `enqueue` on `List`, `Map`, `Set`, `Stack` and `Queue`)
is written out by hand, though, with a comment saying so. If we add a sixth collection type, it isn't checked
until someone adds it to that list.

## Sixteen cases the pass got wrong

The pass landed in late September with six tests. In October, while building the escape checks for
[turf-fuzz](/research/turf-fuzzer), we found sixteen cases it got wrong. In fifteen of them it accepted a real
escape: the program compiled and returned a reference into a dead frame. At `-O0` the read printed garbage once
the next call reused the frame, and at `-O2` it often printed a believable `0`. In the sixteenth it rejected a
correct program. All sixteen are written up in turf-fuzz's [findings
report](https://github.com/turf-lang/turf-fuzz/blob/master/findings/unsound/escape-boundary/report.md), and all
were fixed by mid-October.

### Any loop turned the check off

The first one was the most serious. Any loop between taking `&n` and returning it disabled the check:

```turf
fn make(k: int): &N {
    mut n: N = N::default();
    mut p: &N = &n;
    mut i: int = 0;
    while i < k {
        i = i + 1;
    }
    return p;
}
```

At the top of a loop, the pass merges the path coming from before the loop with the path coming back from the
end of the loop body. On the first round, that second path hasn't been computed yet. The pass treated it as an
empty map, so merging `{p: Stack}` with `{}` gave an empty map and `p` became `Unknown`. `Unknown` is never
flagged, and the empty map carried on around the loop from there.

<Figure caption="The same control-flow graph before and after turflang 9398f38. Treating a path that hasn't been computed yet as empty wiped out every provenance at every loop. Skipping it until it has been computed keeps them.">
  <LoopBug />
</Figure>

[The fix](https://github.com/turf-lang/turf-lang/commit/9398f38) was to skip an incoming path that hasn't been
computed yet, so it leaves the merge unchanged. The null-dereference pass had the same mistake, and we fixed it
the same day.

Around the same time we found that a `give`/`otherwise` expression was always `Unknown`, so `return (c give &n
otherwise &n2)` compiled. A `give` now merges its two branches the same way two paths are merged.

### References stored inside other values

The next eight were cases the original design record had already listed as known gaps. The pass tracked
variables, so it missed a reference that escaped inside something else:

```turf
fn make(): H {
    mut n: N = N::default();
    mut h: H = H::default();
    h.head = &n;
    return h;              // E086: returned inside a struct or array
}
```

The others were variations on the same idea: `heap(m)` where `m.next` holds `&n`, a struct holding `&n` pushed
into a `List`, `&a[i]` of a local array, `h.own.next = &n` two steps through a parameter, and a field of a
parameter passed by value. Fixing them meant tracking individual fields, which the first design had ruled out. We
decided to do it, as long as the pass still never flags a correct program.

That's where places came from ([8e16021](https://github.com/turf-lang/turf-lang/commit/8e16021)). The map is
keyed by paths inside values, storing to a path clears what was known below it, and every sink looks inside the
value it receives. One fact now crosses a function boundary: if every `return` in a function returns one of its
reference parameters unchanged, the caller's argument keeps its provenance through the call. So `return id(&n)`
is an error, and `return id(heap(n))` is not.

### Cases the rule didn't cover

The last six weren't plain bugs. The rule didn't say what should happen, so we had to decide, and each decision
went into the specification.

The first question was what happens when a path that carries `&n` meets a path that doesn't. The pass had merged
them to `Unknown`:

```turf
fn make(c: bool): &N {
    mut n: N = N::default();
    mut p: &N = heap(n);
    if c {
        p = &n;
    }
    return p;              // E086
}
```

We decided that if any path carries `&n`, the escape is real on that path, so the merged value is `MayStack` and
gets flagged ([1d210f3](https://github.com/turf-lang/turf-lang/commit/1d210f3)). That's the top row and left
column of the merge table. It was the one decision that could have broken the promise of no false errors, and it
doesn't, because the program above really does dangle whenever `c` is true.

An error payload, as in `return E1::P(&n);`, is now a sink
([9afd843](https://github.com/turf-lang/turf-lang/commit/9afd843)), because the payload is copied to the heap so
the error can be returned. A call's result counts as long-lived when none of its arguments can reach this frame,
since a function can't return its own locals. So `mut h: &N = mk(); h.next = &n;` is an error
([d5c7825](https://github.com/turf-lang/turf-lang/commit/d5c7825)). The same goes for an element of a standard
collection.

The last decision was about `defer`, and it fixed the one correct program the pass had rejected. A deferred
statement runs when its block exits, after a `return` has already worked out its value. The pass had analysed it
where it was written, so `a()` below was an error. Now the pass runs deferred statements at every exit of their
block, last in, first out ([b7741c0](https://github.com/turf-lang/turf-lang/commit/b7741c0)):

```turf
fn a(): &N {
    mut n: N = N::default();
    mut p: &N = heap(n);
    defer p = &n;          // runs after the return value is taken
    return p;              // accepted: returns the heap copy
}

fn b(): &N {
    mut n: N = N::default();
    mut p: &N = &n;
    defer p = heap(n);     // too late to change what is returned
    return p;              // E086
}
```

Each of the sixteen is now a test in the compiler's
[`tests/39_nullable_references/`](https://github.com/turf-lang/turf-lang/tree/master/tests/39_nullable_references):
a `fail_escape_*` file that expects E086 with the right wording, next to `escape_*_ok` files for the cases that
must keep compiling.

## Keeping it fixed

turf-fuzz's [soundness oracle](https://github.com/turf-lang/turf-fuzz/blob/master/oracles/soundness.py) runs
every night. It builds each test program from three parts: where the reference comes from, which sink it reaches,
and the control flow around the sink.

<Figure caption="The soundness oracle. Every combination that type-checks becomes a small program whose correct result is known in advance. The five cases we had to decide run alongside as fixed tests.">
  <OracleProduct />
</Figure>

If the reference comes from the frame, the program has to fail with E086 and with the wording for its sink.
Rejecting it for the wrong reason counts as a failure too. If the reference is safe, the program has to compile
and print exactly `42` at `-O0`, at `-O2`, and under AddressSanitizer with a garbage collection on every
allocation. Between the escape and the read, each program calls a function that overwrites the stack, so a
reference that does dangle prints garbage instead of a lucky `42`.

## What still gets through

The pass doesn't track an array element written at an index known only at run time, so `a[i] = &n; return a;` is
`Unknown`. It doesn't follow a call result whose arguments might reach the frame. It stops at every cast to a raw
pointer, which only `unsafe` code can write. And a new collection type isn't checked until its methods are added
to the list.

Catching any of these would mean looking beyond one function, or guessing, which the pass isn't allowed to do.
For the cases it does cover, the soundness oracle reruns all 2,662 programs every night, so a regression shows up
the morning after it lands.
